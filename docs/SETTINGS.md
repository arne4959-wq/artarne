# ระบบตั้งค่า (ให้ศิลปินแก้เอง ไม่ต้องแตะโค้ด)

หน้า **manage.html** คือห้องควบคุมของศิลปิน ล็อกอินด้วยอีเมล (ส่งลิงก์เข้าอีเมล ไม่มีรหัสผ่าน ไม่มีปุ่มสมัคร) แล้วแก้เองได้ทั้งหมดนี้:

| แท็บ | แก้อะไรได้ |
|---|---|
| โปรไฟล์ | ชื่อ 3 ภาษา, แนวงาน, เมือง, ปีที่เริ่ม, ประโยคบอกตัวตน, คอนเซ็ปต์, ประวัติ, **รูปโปรไฟล์**, **ทรง/ขนาด/สี 3 สีของตึก**, **ไทม์ไลน์**, ลิงก์ Instagram |
| งานของฉัน | เพิ่ม/แก้/ลบ งาน, **อัปโหลดรูปงาน** (ย่อในเบราว์เซอร์ก่อนส่ง รับรูปจากมือถือได้), ชื่อ, ปี, วัสดุ, ขนาด, และ **คำพูดของศิลปินเอง** (งานนี้บอกอะไร / มาจากไหน / ให้ดูตรงไหน) |
| การสนับสนุน | ดูรายการที่ผู้สนับสนุนแจ้งโอน แล้วกดยืนยันหรือปฏิเสธ (ยังไม่ทำงานจนกว่าจะต่อท่อ "ฉันโอนแล้ว" ดู `docs/GO-LIVE.md`) |
| รับเงิน | ธนาคาร เลขบัญชี QR (ที่แสดงในหน้าบริจาค) และอีเมลที่ใช้ล็อกอิน |

**ศิลปินลงงานเองได้เสรี ไม่ต้องรอใครอนุมัติทีละชิ้น** ที่คุณคุมมีแค่ครั้งเดียวคือ "เปิดตึกให้ศิลปินคนนั้น" (ข้อ ง ข้างล่าง) ส่วนงานที่มีคนร้องเรียน คุณซ่อนได้ภายหลัง (หัวข้อสุดท้าย)

เว็บเป็นไฟล์นิ่ง สิ่งที่ศิลปินกดบันทึกอยู่ใน Supabase ก่อน แล้วขึ้นหน้าเว็บสาธารณะ **ภายในประมาณ 30 นาที** เมื่อระบบสร้างเว็บใหม่ (`.github/workflows/deploy.yml` ดึงข้อมูล รวมเข้า `artists.js` ในเครื่องสร้างเว็บ แล้วสร้างหน้า studio/profile/ภาพแชร์/sitemap ของทุกคน) อยากให้ขึ้นทันทีให้กด Actions → deploy → Run workflow

## ใส่ให้ใช้งานจริง (ทำครั้งเดียว ตามลำดับ)

### ก. ฐานข้อมูล (Supabase → SQL editor)

1. เปิดฐานข้อมูลที่รันแค่ migration 001 ให้ครบ: รันบรรทัดนี้ในเครื่อง แล้ววางผลใน SQL editor กด Run
   ```
   npm run db:bundle | pbcopy
   ```
   มันรวม migration 002–008 เป็นสคริปต์เดียวใน `begin; … commit;` ถ้าผิดตรงไหน ไม่มีอะไรเปลี่ยนเลย (ทดสอบแล้วว่าได้ผลเหมือนรันทีละไฟล์) ถ้า dashboard เตือนว่ามีคำสั่งที่ทำลายข้อมูล (`drop policy`) ให้กดยืนยัน: คือการปิดสิทธิ์ของศิลปินในตาราง payment_notices เก่าตาม migration 003 (ตั้งใจ ตารางยังว่างอยู่) จากนั้น `npm run doctor` ต้องไม่มี FAIL เรื่อง column และ `npm run pull -- --dry` ต้องไม่ error (HTTP 400 = ยังขาดคอลัมน์)
2. Authentication → Sign In / Providers → **ปิด "Allow new users to sign up"** (อยู่ในหัวข้อ User Signups หรือใต้ Email ตามเวอร์ชัน dashboard; ตอนนี้ใครก็สร้างล็อกอินได้) `npm run doctor` บอกได้ว่าปิดแล้วหรือยัง

### ข. อีเมลล็อกอิน (สำคัญที่สุด ถ้าข้ามข้อนี้ ไม่มีศิลปินคนไหนเข้าได้)

3. อีเมลที่ Supabase ให้มาในตัว **ส่งได้เฉพาะสมาชิกทีม Supabase ของคุณ** (คนอื่นจะได้ "Email address not authorized") และจำกัดจำนวนต่อชั่วโมงต่ำมาก ใช้ได้แค่ตอนคุณทดสอบกับอีเมลตัวเอง
   ต้องตั้ง SMTP ของคุณเองที่ Authentication → SMTP Settings (ชื่อเมนูอาจต่างเล็กน้อยตามเวอร์ชันของ dashboard) ตัวเลือกที่ไม่มีค่าใช้จ่าย: **Brevo** (ราว 300 อีเมล/วัน), **Resend** (ต้องมีโดเมนของตัวเอง), **Gmail + App Password** (ง่ายที่สุดถ้ายังไม่มีโดเมน; ต้องเปิด 2-step ก่อน) ใส่ host/port/user/password/ชื่อผู้ส่ง แล้วลองส่งลิงก์ไปหาอีเมลที่ไม่ใช่ของคุณสักฉบับ
4. Authentication → URL Configuration: **Site URL** = ที่อยู่เว็บจริง (ตอนนี้ `https://arne4959-wq.github.io/artarne/`) และใน **Redirect URLs** ใส่ `https://arne4959-wq.github.io/artarne/manage.html` (ถ้าจะลองในเครื่องใส่ `http://localhost:5173/manage.html` ด้วย) ถ้าไม่ใส่ ลิงก์ในอีเมลจะพาไปผิดที่

### ค. ตัวคุณเอง (แอดมิน + ตึกแรก)

5. Authentication → Users → **Add user** ใส่อีเมลคุณ (ติ๊ก auto-confirm ถ้ามีช่องให้)
6. สร้างตึก `arne` พร้อมงาน 3 ชิ้นเดิม (ใช้รูปเดิมใน `art/` ไม่ต้องอัปโหลดใหม่) ผูกกับล็อกอินคุณ และตั้งคุณเป็นแอดมิน:
   ```
   npm run db:seed -- arne อีเมลของคุณ --admin | pbcopy
   ```
   วางใน SQL editor กด Run (สคริปต์พิมพ์ SQL อย่างเดียว ไม่ส่งไปไหน; ถ้ายังไม่มีล็อกอินนั้น มันหยุดพร้อมบอกว่าให้ทำข้อ 5 ก่อน และไม่สร้างอะไรเลย) ออกจากระบบแล้วเข้าใหม่หนึ่งครั้งเพื่อให้สิทธิ์แอดมินมีผล
   ตึกที่มี id ตรงกับที่เขียนมือใน `artists.js` (เช่น `arne`) จะถูกแทนด้วยข้อมูลจริงจากฐานข้อมูลเอง
7. เข้า `manage.html` (ก่อนขึ้นเว็บในข้อ 10 เปิดในเครื่องได้ด้วย `npm run app:dev` แล้วไป `http://localhost:5173/manage.html` ต้องมี Redirect URL นี้ในข้อ 4) → ใส่อีเมล → กดลิงก์ที่ส่งไป → แท็บ "รับเงิน" ใส่ธนาคาร ชื่อบัญชี เลขบัญชี และ QR (ไฟล์รูปจาก BCEL OnePay) → แท็บ "งานของฉัน" เขียนคำเล่าของงานทั้งสามชิ้น (ไม่มีใครเขียนแทนได้)

### ง. ขึ้นเว็บ (GitHub)

8. เอา `.github/workflows/deploy.yml` ขึ้น `main`. โทเค็นในเครื่องไม่มีสิทธิ์ `workflow` เลย push ไฟล์นี้ไม่ได้ ให้สร้างผ่านหน้าเว็บ GitHub: repo → Add file → Create new file → ตั้งชื่อ `.github/workflows/deploy.yml` → วางเนื้อหาไฟล์ (คัดลอกด้วย `cat .github/workflows/deploy.yml | pbcopy`) → Commit (ไฟล์นี้ปลอดภัยที่จะอยู่บน main ก่อน: จนกว่าจะทำข้อ 11 มันรันเฉพาะตอนกดเอง)
9. Settings → Pages → **Source = GitHub Actions**
10. Actions → deploy → **Run workflow** รอจนเขียว (ครั้งแรกอาจ 5–10 นาที) เปิดเว็บเช็ก: ท้ายหน้าจะมีลิงก์ "ตั้งค่า" ไป `manage.html`, ตึก `arne` ยังอยู่ ถ้าแดง เปิดดูบรรทัดที่พังใน log
11. Settings → Secrets and variables → Actions → **Variables** → New repository variable: `AUTO_DEPLOY` = `true` จากนี้เว็บสร้างใหม่เองทุก 30 นาทีและทุกครั้งที่ push (ลบตัวแปรนี้ = หยุดอัตโนมัติ) ตัวแปรเสริม: `SITE_URL` (เมื่อมีโดเมนของตัวเอง), `HIDE_DEMO` = `true` (ซ่อนศิลปินตัวอย่างเมื่อมีศิลปินจริงแล้ว: ดูข้อควรระวังเรื่อง `published-ids.json` ใน `docs/GO-LIVE.md` ก่อน)

### จ. เชิญศิลปินคนต่อไป (ทำทีละคน)

12. ตามที่หน้า join สัญญาไว้ ให้ขอภาพหน้าจอแอปธนาคารที่เห็นชื่อบัญชีก่อน แล้ว Authentication → Users → **Invite user** (อีเมลของเขา; ต้องทำข้อ 3 แล้ว)
13. สร้างตึกของเขา (เปลี่ยน id ชื่อ แนวงาน เมือง และอีเมล) `id` ใช้ตัวพิมพ์เล็ก ตัวเลข และขีด 3–40 ตัว และ **เปลี่ยนทีหลังไม่ได้** เพราะเป็นที่อยู่ถาวรของตึก (`studio-<id>.html`):
    ```sql
    insert into artists (id, user_id, name, name_en, disc, city, approved)
    select 'mali', id, 'มะลิ', 'Mali', 'ริโซกราฟ', 'เวียงจันทน์', true from auth.users where lower(email) = lower('mali@example.com');
    insert into artist_private (artist_id, email) values ('mali', 'mali@example.com');
    ```
    ถ้ายังไม่มีล็อกอินของอีเมลนั้น บรรทัดที่สองจะ error และไม่มีอะไรถูกสร้าง ถ้ายังตรวจบัญชีไม่เสร็จ ใส่ `false` แทน `true` ก่อน แล้วค่อย `update artists set approved = true where id = 'mali';`
14. ศิลปินเปิดอีเมล กดลิงก์ เข้า `manage.html` กรอกโปรไฟล์ เพิ่มงานอย่างน้อย 1 ชิ้น ภายใน ~30 นาทีตึกขึ้นเว็บ (ตึกที่ยังไม่มีงานจะไม่ขึ้น)

## เทียบกับของจริง: ตรวจอะไรแล้ว อะไรยังไม่ได้ตรวจ

ตรวจแล้ว (ในเครื่อง ไม่มีใครใช้จริง):
- สิทธิ์ฐานข้อมูล 100 เช็กใน Postgres จำลอง (`npm run test:db`): ศิลปินแก้ได้เฉพาะของตัวเอง อนุมัติ/ตั้งเป็นแอดมินเองไม่ได้ ซ่อนงานได้เฉพาะแอดมิน และ **ทุกคอลัมน์ที่หน้า manage เขียนอยู่ในสิทธิ์ที่ให้ไว้** (เพิ่มช่องในฟอร์มแล้วลืมให้สิทธิ์ เทสต์จะล้ม)
- ทั้งสายตั้งแต่ศิลปินสดไปจนถึงหน้าเว็บ (`node tests-legacy/run.mjs live`): รวมเข้า `artists.js`, สร้างหน้า studio/profile/ภาพแชร์/sitemap, ข้อความของศิลปินที่เป็นโค้ดอันตราย (`<img onerror>`, `</script>`, เครื่องหมายคำพูด) ถูกแสดงเป็นข้อความเฉย ๆ ทุกหน้า, ศิลปินสดที่มีเลขบัญชีแต่ไม่มี QR ไม่เห็น QR ปลอม
- ตัวสคริปต์ SQL ที่พิมพ์ออกมาทำงานบนสคีมาจริง (migration 001–006) ได้ผลเหมือนกันทั้งแบบรวมและแบบทีละไฟล์

**ยังไม่เคยตรวจกับของจริง** (ต้องตรวจเองครั้งแรกด้วยรูปเล็ก ๆ):
- อัปโหลดรูปขึ้น Supabase Storage จากหน้า manage และรูปโหลดขึ้นหน้าเว็บ (ภาพแชร์ `og/<id>.png` ของศิลปินสดโหลดรูปจากอินเทอร์เน็ตตอน build: ดูภาพที่ได้ว่ารูปขึ้น)
- ลิงก์ล็อกอินทางอีเมลกับ SMTP ที่คุณเลือก และการ redirect กลับ `manage.html`
- การรัน Actions จริง (Chrome บน runner ของ GitHub ฯลฯ) ครั้งแรกให้กดรันเองแล้วดู log
- โปรเจกต์ Supabase ฟรีจะถูกพักถ้าไม่มีการใช้งานนาน ๆ (ตามนโยบายตอนเขียน ตรวจที่ dashboard) การดึงข้อมูลทุก 30 นาทีนับเป็นการใช้งาน แต่ถ้าปิด `AUTO_DEPLOY` นานเกินไปมันอาจถูกพัก

## ซ่อนงานที่ถูกร้องเรียน (แอดมินเท่านั้น)

เมื่อมีคนแจ้งงานชิ้นหนึ่ง (ปุ่ม "แจ้งงานนี้" ในหน้าสตูดิโอส่งอีเมลมาที่ `CONFIG.contact` พร้อมรหัสศิลปินและลำดับงาน) ให้ซ่อนงานก่อนตรวจสอบ โดยรันใน Supabase SQL editor (migration 006 ต้องรันแล้ว):

```sql
-- หา id ของงาน
select id, artist_id, position, title from works where artist_id = 'ใส่-id-ศิลปิน' order by position;
-- ซ่อน (true) หรือเอากลับ (false)
select admin_set_work_hidden('ใส่-uuid-ของงาน', true);
```

คนทั่วไปจะไม่เห็นงานนั้นในการ build ครั้งถัดไป (ภายในประมาณ 30 นาที) ศิลปินเจ้าของงานยังเห็นในหน้า manage พร้อมป้าย "ถูกซ่อนโดยผู้ดูแล" และปลดซ่อนเองไม่ได้
